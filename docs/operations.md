# Установка и эксплуатация Forma AI

## Постоянная установка

Подготовьте Linux VPS с Docker Engine и Compose v2. Создайте две DNS-записи для публичного сайта и студии. Откройте входящие порты 80 и 443. Сборку проверенного кода выполняйте на отдельном runner. Для самостоятельного пилота из доверенной рабочей копии предусмотрена локальная сборка.

```sh
npm run setup -- site.example.org studio.example.org
docker compose --env-file .env -f infra/compose.yaml build web
docker compose --env-file .env -f infra/compose.yaml up -d --no-build
```

Установщик генерирует пароли сервисов, ключ Payload и пару Ed25519. В корне появляется закрытый файл `.env`, в `infra/local/` — политика доступа к S3. Эти файлы нужны при переносе установки. При старте S3 получает отдельную копию своей политики в tmpfs с правами служебного пользователя контейнера. Файл на хосте сохраняет права 0600 даже при разных UID хоста и контейнера. Сохраните их отдельно от Git и копии данных. Для работы с готовым образом укажите в `FORMA_IMAGE` ссылку с OCI digest, загрузите этот образ перед запуском.

Создайте первого владельца из терминала VPS. Пример использует Bash. Запись оператора или редактора создаётся той же командой с ролью `operator` или `editor`.

```bash
read -rs -p 'Пароль владельца (от 14 символов): ' forma_password
printf '\n'
printf '%s' "$forma_password" | docker compose --env-file .env -f infra/compose.yaml exec -T studio node --import tsx scripts/owner.ts owner@example.org owner
unset forma_password
```

Откройте домен студии. Первый выпуск выполняется из демочерновика. Кабинет пишет ревизии страниц в прикладные таблицы PostgreSQL. Payload отвечает за пользователей и сессии. Публичный сайт читает представление активного снимка отдельной ролью. Сервис объектов доступен внутри сети Compose. Изображения PNG и JPEG до 8 МБ адресуются по SHA-256. Публичная выдача проверяет наличие файла в текущем снимке.

## Подключение каналов

Модель получает текст задания и разрешённый контекст. В `.env` укажите полный `MODEL_ENDPOINT`, `MODEL_NAME` и при необходимости `MODEL_KEY`. Для командных задач лимит ответа составляет 1000 токенов, для правки одного свойства — 450. Перечитайте конфигурацию командой `docker compose --env-file .env -f infra/compose.yaml up -d --no-build worker`. Команда подготовки патча читает аналогичные переменные из окружения вызывающей оболочки.

Веб-чат записывает вопрос с ключом повтора. Публичная статья служит заранее утверждённым ответом, срок и видимость проверяются при поиске. При отсутствии источника вопрос попадает к оператору. Посетитель может проверить согласованный ответ в том же диалоге. Для Telegram задайте `TELEGRAM_TOKEN` и включите профиль `--profile telegram`. По умолчанию ответы утверждает человек. `TELEGRAM_AUTO_REPLY=true` включает автоматическую отправку ответов по действующей публичной статье. Неопределённый результат отправки остаётся для сверки.

По умолчанию поиск использует PostgreSQL FTS. Для семантического поиска в веб-чате задайте полный адрес `EMBEDDING_ENDPOINT`, `EMBEDDING_MODEL`, при необходимости `EMBEDDING_KEY`, а также `SEMANTIC_URL=http://search:3110`. Запустите Compose с `--profile semantic`. Отдельный процесс индексирует действующие публичные статьи. При отсутствии текстового совпадения он получает вопрос и возвращает ID и ревизию кандидата. Перед выдачей веб-сервис заново проверяет публикацию, ревизию и срок статьи. После смены профиля векторный индекс перестраивается.

## Согласование архитектуры

- Старые страницы и их подписываемое содержимое сохраняют формат v1. В v2 ширина задаётся полем `widthPercent`, минимальная высота — `minHeightPx`. Настройки наследуются от телефона к планшету и компьютеру. На границе старого API ширина проецируется на сетку 1–12. Предыдущие веб-выпуски остаются доступными для отката.
- Межканальный контракт и откат контента входят в первый веб-выпуск. Во втором этапе подключаются предложения, знания и адаптеры ботов. Нативная доставка имеет отдельный цикл. Так веб- и мобильный клиенты можно выпускать в разное время.
- Снимок связывает контент, хеши медиа, версию схемы, код и сборку. Студия подписывает решение владельца по идентификатору операции, целевому снимку и поколению активного маршрута. Исполнитель проверяет подпись, переключает снимок и проверяет публичную страницу и API. После сбоя он продолжает незавершённую проверку. Данные заявок и диалогов находятся в отдельных таблицах.
- `infra/build-code.sh REV TAG` собирает указанную Git-ревизию из архива на отдельном Docker-runner. Патчи ИИ проходят review как обычные изменения кода. Сборка по SHA и проверка Compose в CI предшествуют доставке образа. Подключение промышленного OCI-реестра, подпись распространяемых тегов, выдача прав магазинам и инфраструктура переключения версий серверного кода настраиваются владельцем.
- На уровне веб-пилота документ проекта представляет одну страницу. Поддерживаемые рендереры перечислены в контракте. Для нового нативного действия понадобятся реализация в клиентах, контрактная проверка и механизм совместимости. Профиль проекта и настройки интеграций отделены от общих контрактов.

## Восстановление

Запустите `bash infra/backup.sh /путь/к/новому-каталогу` из корня рабочего проекта. Выберите защищённое хранилище вне VPS. Скрипт делает согласованный `pg_dump`, копирует объекты с проверкой хешей и сохраняет Git-историю в bundle. Файл `SHA256SUMS` появляется после успешного завершения. Каталог содержит рабочие данные. Защита и шифрование места хранения находятся под управлением владельца.

Для восстановления клонируйте `source.bundle`, верните `.env` и `infra/local/s3.json` из отдельного защищённого комплекта, предоставьте исходный образ. Из чистой установки выполните

```sh
bash infra/restore.sh /путь/к/снимку
docker compose --env-file .env -f infra/compose.yaml up -d --no-build
```

Скрипт проверяет контрольные суммы и пустую целевую БД, восстанавливает данные в отдельную БД, загружает медиа и переключает имя БД после успешной загрузки. Откройте активный сайт, последнее изображение, заявку и историю задачи. Восстановление проверяется тестом `npm run test:compose`.

Для восстановления на момент времени предусмотрен дополнительный профиль `infra/pitr.yaml`. Подключите принадлежащий владельцу внешний том `WAL_ARCHIVE_DIR`, выдайте пользователю PostgreSQL право записи и добавьте `-f infra/pitr.yaml` к запуску Compose. Для полноценного PITR нужны физическая базовая копия PostgreSQL, непрерывная последовательность WAL и испытание восстановления на согласованном объёме. Цели пилота — потеря данных до 15 минут, восстановление за 4 часа и откат контента за 30 секунд. Результаты локальной проверки служат функциональной приёмкой. Эксплуатационные показатели измеряются на VPS бизнеса.
