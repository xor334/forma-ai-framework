# Архитектура модульной Forma AI

Владелец описывает бизнес-задачу и приводит пример, по которому примет результат. Он открывает репозиторий или свой форк в VS Code, Claude Code, Codex либо другой среде. Помощник видит те же контракты, шаблоны и команды, что и человек. Установленный модуль продолжает работать, когда редактор закрыт. Выбор модели и инструмента разработки принадлежит владельцу.

## Что поставляется сейчас

| Область | Есть в репозитории | Следующий критерий готовности |
| --- | --- | --- |
| Разработка модулей | Шаблон автономного сервиса, Dockerfile, манифест v1, проверка графа и отдельный тест. Можно создать модуль в форке без правок ядра | Установить проверенный образ и увидеть модуль в админке |
| Базовая установка | Веб-пилот, студия, PostgreSQL, роли процессов, утверждение и откат снимка контента, резервирование и проверка восстановления | Выпуск и откат отдельно устанавливаемого сервиса по digest |
| Админка | Вход и глобальные роли owner/editor/operator, редактирование страницы, знания, обращения и выпуски | Пользователи и роли по модулям, каталог с редактированием настроек, просмотр таблиц и записей всех модулей и ядра |
| SQL и сеть | Пилот использует отдельные SQL-роли и общую сеть Compose. Манифест описывает потребление SQL-контракта и запросы сети | Выдача и отзыв реальных прав, DMZ, запрет произвольных входящих, исходящих и межмодульных соединений |
| MCP | Локальный запуск подготовленного stdio-образа в Docker с закрытой сетью. Манифест описывает инструменты и зависимости | Управляемая установка MCP-серверов, подключение внешних серверов, сервер инструментов самой Forma и аутентификация удалённых клиентов |
| Качество | Обязательный PostgreSQL-сценарий пилота, план затронутых модулей, выборочные проверки и сборки в CI | Добавлять проверки новых базовых функций в обязательный сценарий по мере их реализации |

## Ядро и модули

Ядро отвечает за идентификацию, права и секреты, админку, реестр контрактов, обмен сообщениями, изолированное исполнение, наблюдение, выпуск и восстановление. Для небольшого проекта несколько обязанностей можно разместить в одном процессе. Сайт, CRM, отраслевые правила, боты, модели и прикладные ИИ-агенты подключаются по потребности. Сценарии курса служат заданиями для форков. Их бизнес-логика остаётся вне обязательной поставки.

Единица разработки, тестирования, сборки и эксплуатации — модуль. Его ID сохраняется при обновлении, образ и миграции версионируются. В собственной директории находятся контракт, исходники, тесты, Dockerfile и описание. Для простой функции достаточно кода внутри существующего модуля. Свой сервис оправдан, когда нужны отдельные данные, полномочия, цикл выпуска или масштабирование.

Стандартный шаблон использует Node.js. Сервис на другом языке может предоставить такой же внешний контракт. Доверенные адаптеры в `business/extensions/` исполняются в процессе студии при сборке страницы пилота. Новый исполняемый сервис размещают в `business/modules/` и собирают в отдельном контексте. Встраивание сгенерированного кода в процесс студии наделило бы его правами студии.

## Обязательная админка

| Раздел | Что делает пользователь с полномочиями администратора |
| --- | --- |
| Пользователи и роли | Выбирает другого пользователя, модуль и роль, выдаёт или отзывает доступ. Один человек может быть редактором в одном модуле и наблюдателем в другом. Назначение хранится как связь пользователя, модуля и роли. История содержит автора и время изменения |
| Модули | Видит полный набор установленных модулей, их описания, версии, состояние, зависимости и настройки. Меняет настройки в форме, построенной по манифесту. Видит причины сбоя, запрошенные и выданные доступы |
| Данные | Видит все таблицы проекта, включая ядро и схемы всех модулей. Открывает столбцы, строки и значения с постраничной выдачей. Список формируется по каталогу БД, поэтому новая таблица появляется после миграции без отдельного экрана |

Доступ пользователя в админку и полномочия работающего сервиса проверяются отдельно. Обозреватель использует учётную запись чтения, проверяет выбранные имена по каталогу, ограничивает объём ответа и время запроса. Секреты интеграций хранятся в хранилище секретов, в настройках видны ссылки. Изменения прав, настроек и активной версии фиксируются в журнале.

## Владение данными и связь модулей

Для одной установки используем одну базу PostgreSQL с отдельной схемой и рабочей ролью на модуль. Миграции выполняет отдельная роль. Писать в бизнес-таблицы может владеющий ими модуль. Опубликованные контракты позволяют выбрать способ взаимодействия по задаче.

| Механизм | Когда применяется | Гарантия контракта |
| --- | --- | --- |
| Запрос API | Нужен немедленный результат с бизнес-проверками | Версия, типы входа и ответа, права и тайм-аут |
| Команда | Один исполнитель меняет бизнес-состояние | Ключ операции, определённый результат при повторе и журнал |
| Событие | Изменение состояния интересно нескольким потребителям | Одна транзакция сохраняет факт и запись для доставки. У каждого подписчика собственное подтверждение. Повторы обрабатываются по ID события |
| Прямое SQL-чтение | Нужны отчёт, выборка или JOIN по данным другого модуля | Поставщик публикует версионированное представление. Роль потребителя получает USAGE на схему и SELECT на согласованный объект |
| Инструмент MCP | Среда разработки или прикладной агент запрашивает конкретное действие | Типизированный инструмент, идентификация вызывающего, проверка доступа к каждой операции |

Например, склад публикует `sql:stock@1`, а продажи объявляют зависимость от этого контракта. Продажи читают `inventory_read.stock_v1` прямо из БД и могут делать JOIN со своими записями. Резервирование остатка выполняет команда склада. Переход на `stock_v2` допускает параллельную поддержку обеих версий. Удаление v1 блокирует проверка реестра, пока на неё ссылается потребитель. Декларация зависимости нужна для проверки совместимости. Действительный SQL GRANT выдаёт администратор через механизм установки.

Для первой очереди достаточно PostgreSQL. Работники берут задачи в аренду, после сбоя задача становится доступна повторно. Число процессов увеличивают у модуля с растущей очередью, наблюдая за возрастом старейшего задания, задержкой и долей ошибок. При внешнем побочном действии используйте поддерживаемый поставщиком ключ идемпотентности или сверку неопределённого результата. Состояние модуля и контрольные точки сохраняются вне процесса. Для переживания потери узла нужны отдельные узлы и проверенное восстановление.

## Сеть и инструменты

Целевая сетевая политика закрывает входящий, исходящий и боковой трафик по умолчанию. DMZ содержит публичный обратный прокси. Админка, модули, исполнитель выпуска и БД находятся во внутренних сегментах. Правило содержит инициатора, получателя, протокол, порт и назначение. Порт TCP 443 сам по себе не ограничивает домен или маршрут. Это обеспечивают шлюз, проверка подлинности и политика исходящего трафика.

| Разрешённый путь при соответствующей настройке | Граница |
| --- | --- |
| Посетитель → публичный шлюз → опубликованный маршрут | Порты и маршруты указываются явно. Административный вход доступен через выделенный путь, например VPN |
| Модуль → PostgreSQL по TCP 5432 | Сетевое правило допускает соединение, служебная роль ограничивает доступ к таблицам |
| Модуль → адаптер → адрес поставщика по TCP 443 | Разрешения на назначение и операцию проверяются отдельно. Секрет получает адаптер |
| Среда разработки → MCP тестового стенда | Доступ ограничен проектом, окружением и разрешёнными инструментами |

Политику реализуют сетевые средства хоста или оркестратора вместе с прикладным шлюзом. Проверка выпуска должна наблюдать успешное разрешённое соединение и отклонённые попытки входа, исходящего и межмодульного трафика. Простое отсутствие опубликованного порта в Docker решает лишь задачу внешнего входа.

Среда разработки получает рабочую копию, публичные контракты, подготовку изменения, изолированные проверки и передачу версии на выпуск. Выдача рабочих секретов, изменение политики доступа и активация выпуска принадлежат оператору установки. Права терминала и редактора ограничивает окружение пользователя. Локальная команда `ai:propose` выдаёт патч на выбранные файлы одного модуля или доверенного адаптера. Правила в AGENTS.md направляют работу помощника. Для технического ограничения файлов, сети и ключей нужна изолированная рабочая среда.

### MCP-серверы

Forma должна уметь запускать собственные и подключать внешние MCP-серверы. Любой совместимый клиент получает разрешённые инструменты, их описания и схемы. Собственный сервер Forma должен открывать каталог контрактов, тесты на стенде и подготовку версии. Инструменты рабочей установки имеют отдельные полномочия. Прикладной агент внутри системы проходит те же проверки, что и иной клиент.

Готовый локальный путь для stdio выглядит так. Соберите совместимый MCP-сервер в образ, который работает под непривилегированным UID и обменивается сообщениями через stdin/stdout. Получите его фактический ID командой `docker image inspect --format '{{.Id}}' ИМЯ_ОБРАЗА`. В MCP-клиенте задайте команду `sh` и два аргумента — абсолютный путь к `scripts/mcp-stdio.sh` и полученный `sha256:…`. Требуется запущенный Docker. Клиент запускает контейнер с закрытой сетью, без подключения каталогов хоста, с корневой ФС только для чтения и ограничениями памяти, CPU и процессов. Для диагностики сервер пишет в stderr. Для удалённого сервера предусмотрен Streamable HTTP через аутентифицированный шлюз. Внешние вызовы, выдача секретов и удалённая установка требуют отдельного настроенного окружения.

## Качество, стоимость и выпуск

План учитывает изменённые файлы, поставщиков и потребителей контрактов. Включает удаления и переименования. Локальный запуск сравнивает рабочую копию с Git-ревизией и учитывает новые файлы. Для PR CI проверяет результирующую версию относительно базовой ветки. На первом запуске без базы применяется полный план. Результат публикуется в сводке GitHub Actions.

| Изменение | Проверки сверх обязательного сценария | Кандидаты на выпуск |
| --- | --- | --- |
| Документация | Редакторская проверка изменённого текста и команд | Пусто |
| Только тест модуля | Тесты этого модуля | Пусто |
| Внутренняя реализация | Проверки модуля, сборка его собственного образа | Изменённый модуль |
| Манифест, контракт или миграция | Модуль и затронутые потребители по графу, включая транзитивные зависимости. Для миграции нужен прогон с прежней схемы | Проверяются артефакты и конфигурация реально изменившихся модулей |
| Общая или неизвестная часть платформы | Расширенная проверка пилота и тесты всех модулей | Область установки определяется разницей проверенных артефактов и конфигураций |
| Удаление модуля | Проверить оставшихся потребителей. Отдельно определить судьбу данных и совместимость | Вывод из эксплуатации требует решения владельца |

Обязательный тест сейчас проходит на реальной временной PostgreSQL. Он проверяет отказ в публикации для редактора, выпуск владельцем, возврат после ошибки публичной проверки, сохранность заявки при повторе и изоляцию закрытых таблиц от веб-роли. Для целевой платформы обязательный маршрут дополнится входом в админку, назначением роли в одном модуле, проверкой роли в соседнем, изменением настройки и чтением строки новой таблицы. Проверка от имени сервиса должна подтвердить разрешённый SELECT, отказ в чужой записи и отказ по закрытому сетевому маршруту.

При исправлении дефекта добавьте минимальный тест воспроизведения. Для контрактов проверьте потребителя на версии поставщика из этого изменения. Для миграции проверьте обновление данных, для прав — разрешённое и запрещённое действие. Браузерные прогоны нужны для затронутых интерфейсов. Бизнес-модель и внешний ИИ не участвуют в обычном CI. Используйте локальные ответы, ошибки и тайм-ауты. Оценка качества живой модели запускается отдельно при смене промпта, модели или выбора инструментов с явным набором примеров и бюджетом.

Проверка потребителя сама по себе не повод перезапускать его в эксплуатации. Проверенный образ продвигают по одному digest, миграции применяют адресно, конфигурацию сравнивают по версии. После смены проверяют готовность и бизнес-маршрут затронутого модуля. Откат кода требует совместимой схемы. Необратимые изменения данных требуют отдельного плана восстановления. CI этого репозитория тестирует и собирает кандидатов. Полномочия и подключение к промышленному деплою остаются у владельца.

## Как принять эту архитектуру в форке

1. Создать пустой модуль штатным шаблоном и проверить его без изменения веб-пилота.
2. Подключить второй модуль к версионированному контракту первого. Проверить, что изменение контракта выбирает тесты обоих, а исправление внутренней функции выбирает только первого.
3. Для установки проверить роли, данные, сеть и отключение модуля на отдельном стенде. Сопоставить результат с таблицей готовности выше.
4. Сохранять версию upstream, по которой проверена совместимость. Правки ядра и прикладные изменения рассматривать отдельно. Критические проверки в публичном проекте целесообразно закрепить как обязательные для слияния. Владелец форка контролирует собственные настройки Git и CI.
