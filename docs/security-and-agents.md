# Границы доступа и работа агентов

Целевая схема для установки на VPS владельца. Редактор, API, очередь, агенты и опубликованный проект работают в его инфраструктуре. Первичную установку выполняет владелец под учётной записью администратора сервера. Локальный координатор выдаёт исполнителям удостоверения проекта. Для работы достаточно локальных служб и выбранных интеграций.

## Где выполняется запрос

Владелец задаёт адрес API, идентификатор модели и ссылку на секрет. При подключении исполнитель проверяет доступные функции отдельными пробами: генерация текста, структурированный ответ, вызов инструментов. Для поиска по знаниям задаётся отдельный профиль эмбеддингов. Профиль определяет допустимую категорию данных, бюджет и тайм-аут. При недоступности провайдера задача сохраняет состояние. Смену получателя данных подтверждает владелец.

| Получатель | Какие данные можно передать |
| --- | --- |
| Выбранная модель | Запрос, разрешённые фрагменты истории и источников. Для внешнего API интерфейс показывает получателя до включения профиля. |
| Сервис эмбеддингов | Только фрагменты источников, для которых разрешена индексация этим сервисом. Для закрытых документов владелец может выбрать локальную модель. |
| Telegram | Ответ и выбранное вложение в исходный чат. Токен получает только адаптер канала. |
| Реестр пакетов и образов | Сборщик читает зафиксированные зависимости из разрешённых реестров. Публикация образов доступна отдельному исполнителю. |

Сгенерированный код собирается во временной изолированной среде с ограничениями CPU, памяти, времени и сети. Сборщику выдаются копия исходников и временный каталог. Рабочая БД, ключи модели, домашний каталог хоста и сокет контейнерного движка исключены из среды. Исполнитель релиза принимает digest проверенного артефакта и записывает результат переключения трафика. [Режим rootless](https://docs.docker.com/engine/security/rootless/)

## Бот и база знаний

Для MVP предлагается общий движок диалогов на TypeScript. Веб-чат и адаптер Telegram на grammY приводят сообщения к одному входному событию. Для Telegram на VPS достаточно long polling. Исполнитель продвигает offset после надёжной записи входящего события. При переходе на webhook проверяет секрет Telegram и подтверждает запрос после записи. [grammY](https://grammy.dev/guide/) · [Telegram Bot API](https://core.telegram.org/bots/api)

API определяет организацию, проект и личность из проверенной сессии. Идентификатор чата Telegram становится идентификатором клиента только после явной привязки аккаунта. Публичный бот видит опубликованные общедоступные документы. Авторизованный клиент дополнительно видит материалы, разрешённые ему лично. Внутренним агентам выдаются права по роли и задаче.

Полнотекстовый и векторный поиск применяют права организации, проекта и аудитории в запросе к БД. Рабочая роль БД имеет ограниченные привилегии и подчиняется политикам доступа к строкам. Каждый фрагмент хранит идентификаторы документа и версии. Перед выдачей ответа движок повторно проверяет права на использованные источники. Отзыв доступа начинает действовать сразу, включая кэш. При недостатке оснований бот уточняет вопрос или передаёт обращение оператору. Текст источника не предоставляет разрешений на вызов инструментов. [PostgreSQL RLS](https://www.postgresql.org/docs/current/ddl-rowsecurity.html) · [pgvector](https://github.com/pgvector/pgvector)

## Как команда меняет сайт

После первого успешного релиза координатор активирует маркетолога, аналитика и поддержку. Общий чат, обсуждение блока и внутренний поток задачи имеют собственные идентификаторы и права. Каждая передача работы указывает автора, адресата, задачу и версию результата. Координатор ограничивает число шагов, время и стоимость обсуждения.

1. Поддержка замечает повторяющийся вопрос о сроках ответа студии. Она передаёт маркетологу количество обращений и обезличенную формулировку.
2. Маркетолог предлагает пояснение под формой. Аналитик задаёт событие успешной отправки и критерий оценки. Срок ответа подтверждает владелец.
3. Разработчик готовит изменение для конкретного блока, тест и предпросмотр. Владелец видит тексты, события и разницу с опубликованной версией.
4. Владелец одобряет конкретную версию изменений. Изменение diff аннулирует это одобрение. Расход рекламного бюджета и массовая рассылка требуют собственных разрешений. Обычный ответ на входящий запрос разрешает заранее заданная политика канала.
