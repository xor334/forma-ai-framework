# Передача базы предпринимателю

## Первый выпуск автора

Автор публикует исходный Git-репозиторий в своей организации, выбирает условия распространения собственных материалов и проверяет лицензии зависимостей. Для эксплуатационной версии выпускает подписанный тег, перечень изменений, поддерживаемые версии, инструкцию миграции и границу отката. Публичный ключ верификации передаётся по независимому доверенному каналу. Локальный коммит в этом архиве служит исходной историей архитектурного прототипа.

Создавайте серверные репозитории пустыми, если будете переносить в них уже существующую историю. Владелец может передать содержимое этого архива в свой remote, сохранив исходный коммит и ветку main. Для GitHub, GitLab и самостоятельно размещённых Git-площадок применимы те же обычные операции fetch, merge и push.

## Как бизнес получает собственную историю

Для открытого проекта подходит Fork на выбранной площадке. На GitHub прямой форк открытого upstream также открыт. Для закрытого бизнеса создайте отдельный приватный репозиторий и перенесите туда исходную историю в рамках выбранной автором лицензии. Другой вариант — разрешённый форк закрытого upstream при подходящих правилах организации. Кнопка Use this template в GitHub создаёт отдельную историю и потому неудобна, если обновления будут регулярно сливаться через Git.

Вариант для владельца, у которого есть адрес исходного `UPSTREAM_URL` и пустого приватного `BUSINESS_ORIGIN_URL`. Эти две переменные он устанавливает сам. Убедитесь, что второй адрес действительно принадлежит бизнесу и его видимость настроена до первой отправки.

```sh
git clone --origin upstream "$UPSTREAM_URL" my-business
cd my-business
git remote add origin "$BUSINESS_ORIGIN_URL"
git push -u origin main
npm test
npm run init:project -- sever-coffee "Кофейня Север"
git add business/project.json
git commit -m "Настроить проект Кофейня Север"
git push origin main
```

Для уже настроенной защиты главной ветки коммит с бизнес-профилем отправляют рабочей веткой и принимают через PR/MR. Привилегии CI и права деплоя настраиваются владельцем отдельно. Фактический деплой и домен появляются при внедрении соответствующего этапа архитектуры.

## Как принимать исправления базы

У автора отдельная последовательность версий ядра. У каждого бизнеса своя последовательность релизов продукта и отдельные номера iOS/Android. Подписанный тег ядра не является разрешением на публикацию клиентского сайта.

Пример процедуры для будущего подписанного релиза. Переменная `BASE_TAG` задаётся именем нужного тега после чтения его журнала изменений. Проверяйте подпись ожидаемым доверенным ключом автора.

```sh
git fetch upstream "refs/tags/$BASE_TAG:refs/tags/$BASE_TAG"
git verify-tag "$BASE_TAG"
git switch -c "upgrade/$BASE_TAG" main
git merge --no-ff "$BASE_TAG"
npm test
```

Перед слиянием в main инициатор проверяет разницу, объясняет конфликты и порядок миграции, описывает затронутые расширения и прогоняет тесты каналов на staging. Если PR конфликтует с кастомным виджетом бизнеса, владелец проверяет этот виджет на настоящих размерах экранов и на сохранённых документах предыдущей версии. Обновление остаётся в ветке до решения владельца. При срочном исправлении допускается отдельный backport в поддерживаемую линию с собственными тестами и ссылкой на исходный коммит.

Общее ядро принимает расширения через реестр типов, каналов и разрешённых действий. Индивидуальное изменение ядра бизнес фиксирует отдельным коммитом. Согласованный универсальный патч можно передать upstream после удаления брендовых данных, секретов и логов клиента.
